# P2 data plan — reported, not executed

**Status:** proposal under P2-R3 E. Nothing here has been downloaded, trained or evaluated.
**Decision pending (P2-R3 F-3):** the data plan is chosen by Josh and the supervisor.

---

## E-1 Plan 1

**Two datasets, two jobs.**

1. **OPV2V answers the F-representation question.** Development on OPV2V `validate` with the P1
   checkpoint, under the (now closed) sparse-line protocol, archived in `archive/p2-sparse-exploratory/`. `test` and Culver-City stay prohibited
   (`p2_protocol.md` C-8).
2. **V2V4Real carries the final system.** One **unified checkpoint is trained on V2V4Real**, and every
   action and every baseline uses that one checkpoint — so a comparison between actions is never also a
   comparison between perception models.

**Proposed V2V4Real division** (official split sizes quoted from the dataset paper: 14,210 / 2,000 /
3,986 frames):

| role | data | why |
|---|---|---|
| checkpoint training | official `train`, minus a scene-disjoint hold-out | the perception model's own training data |
| checkpoint selection (epoch) | the scene-disjoint hold-out carved from official `train` | keeps official `validate` unseen by perception training **and** by checkpoint selection |
| P2 development | official `validate` | policy and representation development for the final system |
| P2 confirmatory evaluation | official `test` | opened once, after stage-2 lock |

**Open before this plan can be locked:**

* **Scenes per split are not stated in the dataset paper** (it gives 67 scenarios in total and frame
  counts per split). The confirmatory statistic is a scene-level bootstrap, so the number of test
  scenes decides how coarse the intervals will be. It must be counted from the downloaded directory
  structure before lock.
* **A V2V4Real checkpoint must keep the same detection range, voxel size and backbone strides** if any
  measurement made on the OPV2V checkpoint is to carry over; a different range changes the transmitted
  tensor and every payload figure derived from it.
* **Data licence:** no data licence is stated on the V2V4Real download page (see `p2_protocol.md` C-8);
  confirm with the provider.

**GPU estimate:** `gpu_estimate.md`, generated by `gpu_estimate.py`. It is a range built from P1's
measured per-frame costs on this machine and two named assumptions; nothing has been run. Its first
replacement is a one-epoch timing probe once the plan is approved.

## E-2 OPV2V `train` is not confirmatory data

**The OPV2V `train` scenes were used to train the perception checkpoint.** A result on them is a
result on data the system has already seen, and it cannot serve as confirmatory evidence for the
system as a whole. The same holds for OPV2V `validate`, which P1 used for model selection and P2 uses
for development.

## E-3 Zero-shot transfer is optional, and is not the main confirmation

Running the **P1 checkpoint unchanged on V2V4Real** is kept as an **optional** evaluation of the method
under domain shift. It is **not** the main confirmation.

**The degradation reported in the V2V4Real paper is not quoted as an expected value for this
checkpoint.** That figure describes their models under their training; it is not a prediction for the
P1 checkpoint, and no expectation for this checkpoint is written down before it is measured.
